Rule examples

Rules that work together.

One rule moves one kind of mail. These recipes combine them: shared lists, senders your provider vouches for, tags that later rules route on, and actions that wait. Every key is in the rules reference.

Hold new mail for your phone Move only verified finance mail Keep security mail out of the automated pile Tag, hold, then route parcel mail Sweep promotions, keep the receipts File a shop that mails through a newsletter service File work mail, minus its bots Mark mail from outside the team Delete CI mail once seen Keep overdue invoices in view Tidy a folder that is not INBOX Archive the rest, last

Order matters. Rules run in file order, top to bottom, on every sync. The recipes are written in the order they would sit in one rules.toml, so the stop in an early rule decides what the later ones see. Replace the .example domains and addresses, the account name and the folder names with your own.

Hold new mail for your phone

Mail apps on a phone mostly notify only for INBOX. A rule with stop near the top keeps every rule below it away from a message for a while, so the phone sees it before it is sorted. There are two ways to write it.

Hold everything for 15 minutes. Simple, but it also delays rules that only tag or mark read, and every route.

rules.toml
[[rules]]
name = "hold new mail for the phone"
match.younger_than = "15min"
actions.stop = true

Hold only what matters: banks, school, sign-in codes. Everything else is sorted at once, and only the mail you would pick up your phone for waits. The subjects are a list, since later recipes need the same pattern.

rules.toml
[lists]
security_subjects = { regex = "sign-?in|new device|verification code|magic link" }

[[rules]]
name = "hold important mail for the phone"
match.any = [
  { from_domain = ["bank.example", "school.example"] },
  { subject = { list = "security_subjects" } },
]
match.younger_than = "15min"
actions.stop = true

Pick one. To delay only a move and let tagging run, give that one rule an after, as in Delete CI mail once seen.

Move only verified finance mail

Anyone can write paypal.com in a From line. authenticated holds only when your provider checked the signatures that prove a message came from that domain (DKIM and DMARC). Real bank mail is filed, and a lookalike stays in the inbox, flagged. One [lists] entry feeds both rules.

Keep the second rule. Without it, mail that fails the check stays in the inbox unflagged, looking just like the real thing next to it.

Needs the account's trusted_authserv_ids. Without it no mail counts as authenticated: the first rule never fires, and the second flags all of it. The tag needs a server that accepts custom keywords.

rules.toml
[lists]
finance = ["bank.example", "paypal.com"]

[[rules]]
name = "finance, verified"
match.from_domain = { list = "finance" }
match.authenticated = true
actions.move = "Finance"
actions.stop = true

[[rules]]
name = "finance lookalikes"
match.from_domain = { list = "finance" }
match.authenticated = false
actions.tag = "$Suspicious"
actions.flagged = true
actions.stop = true

Check that it works before you rely on it. rules check warns about an account without the setting. headers on a mail you received shows the server name after Authentication-Results:, which account trust adds. Then rules test should list a real bank mail under the first rule, not the second.

$ postvak rules check
$ postvak headers UID
$ postvak account trust ACCOUNT mx.example.com
$ postvak rules test "finance, verified"

Keep security mail out of the automated pile

Tag in one rule, route on the tag in the next: a rule sees what the rules above it changed in the same sync. The first rule tags security alerts and sign-in codes. The second clears mail from no-reply addresses out of the inbox, except what the first one tagged, so a sign-in code from a no-reply address stays where you will see it.

It reuses security_subjects from the hold. If you paste a regex into a second rule, make it a list instead: copies drift apart without anyone noticing, and a list changes every rule that uses it at once.

Tags are IMAP keywords, which Thunderbird and other clients show as tags. They start with $ here, a common convention for keywords; any name without spaces works.

Needs a server that accepts custom keywords.

rules.toml
[lists]
bots = { regex = "no-?reply|notifications?@" }

[[rules]]
name = "tag security mail"
match.subject = { list = "security_subjects" }
actions.tag = "$Security"

[[rules]]
name = "automated mail out of the inbox"
match.from = { list = "bots" }
match.none = [{ tag = "$Security" }]
actions.move = "Automated"
actions.notify = false

Tag, hold, then route parcel mail

A rule in the middle of a chain can pause it. The first rule tags parcel mail by carrier or subject. The second stops at mail that is tagged, unread and less than a day old, so a new delivery notice stays in INBOX. The third moves everything tagged once the hold lets go: when you read it, or after a day.

Keyword lists need your mail's languages. In a Dutch mailbox an English-only list (delivered, on its way) misses most of it, so this one has bezorgd and onderweg too.

rules.toml
[lists]
carriers = ["postnl.nl", "dhlparcel.nl", "dpd.nl", "ups.com"]
parcel_subjects = { regex = "delivered|on its way|bezorgd|onderweg|pakket" }

[[rules]]
name = "tag parcels"
match.any = [
  { from_domain = { list = "carriers" } },
  { subject = { list = "parcel_subjects" } },
]
actions.tag = "$Delivery"

[[rules]]
name = "hold unread parcels"
match.tag = "$Delivery"
match.read = false
match.younger_than = "1d"
actions.stop = true

[[rules]]
name = "route parcels"
match.tag = "$Delivery"
actions.move = "Parcels"

With a single route, actions.after = ["read", "1d"] on the third rule says the same thing more plainly than the hold, or than a hand-written none = [{ read = false, younger_than = "1d" }]. Either way, mail you never read moves once a day has passed. The hold rule pays off when several rules below it route the same tag, or should all wait.

Sweep promotions, keep the receipts

A promotions rule is usually the first one people write, and the exclusions are where it goes wrong: an order confirmation, a reply in a thread, a bounce or a sign-in code that happens to carry an unsubscribe link. Two lists hold the exclusions, written as literal strings in single quotes so the regex needs no extra backslashes. The tag from the security rule keeps sign-in codes out.

Move promotions to a folder, not to Junk: junk trains your server's spam filter, and newsletters you signed up for are not spam.

rules.toml
[lists]
transactional = { regex = "order|bevestiging|confirm|receipt|invoice|factuur|e-ticket" }
replies_and_bounces = { regex = '^\s*(re|fwd?|antw|doorst)\s*:|delivery status|undeliver' }

[[rules]]
name = "promotions"
match.header.List-Unsubscribe = { regex = "." }
match.none = [
  { subject = { list = "transactional" } },
  { subject = { list = "replies_and_bounces" } },
  { tag = "$Security" },
]
actions.move = "Promotions"
actions.notify = false

Add replies_and_bounces to the none of any rule that matches on subject keywords: a Re: about an invoice is a conversation, not an invoice.

File a shop that mails through a newsletter service

Many shops send promotions through a service such as Mailchimp or Sailthru, so the address is the service's domain and the shop's name appears only in the display name. from_domain reads only the address; from reads the whole header, display name included. This rule uses both on purpose, and keeps the shop's orders out with the transactional list.

A display name is whatever the sender writes, and anyone using that service can write "Brand". Fine for filing; never use it for mail you would act on, such as payments.

rules.toml
[[rules]]
name = "brand promotions"
match.any = [
  { from_domain = "brand.example" },
  { from_domain = "esp.example", from = { contains = "Brand" } },
]
match.none = [{ subject = { list = "transactional" } }]
actions.move = "Shopping/Brand"

File work mail, minus its bots

Nest none inside any: each entry of any is a set of conditions that must all hold, and can exclude mail of its own. This files mail from colleagues, but not their build bots, together with anything sent to your work alias. It reuses the bots list.

rules.toml
[[rules]]
name = "work, minus the robots"
match.any = [
  { from_domain = "work.example", none = [{ from = { list = "bots" } }] },
  { alias = "me+work@example.com" },
]
actions.move = "Work"

Mark mail from outside the team

to_domain reads the To header, from_domain the sender's address and never the display name. Together they tag mail sent to your company from anywhere else.

Needs a server that accepts custom keywords.

rules.toml
[[rules]]
name = "tag external mail to the team"
match.to_domain = "work.example"
match.none = [{ from_domain = "work.example" }]
actions.tag = "$External"

Delete CI mail once seen

GitHub marks its build mail with an X-GitHub-Reason header. after takes a list and waits for whichever comes first: you read the message, or two days pass. A delete keeps an .eml copy in Postvak's trash, so postvak trash restore brings it back.

rules.toml
[[rules]]
name = "CI mail, once seen"
match.header.X-GitHub-Reason = { equals = "ci_activity" }
actions.delete = true
actions.after = ["read", "2d"]

Keep overdue invoices in view

Archive invoices, except reminders, whether the reminder is in the subject or only in the text. HTML mail is converted to text before the body regex reads it.

Needs the body of new mail in the rule's folder, which Postvak downloads for this rule. A message whose body could not be downloaded never matches, even through none, so it stays in the inbox.

rules.toml
[[rules]]
name = "overdue invoices stay put"
match.subject = { contains = ["invoice", "factuur"] }
match.none = [
  { subject = { contains = ["overdue", "reminder", "herinnering"] } },
  { subject = { list = "replies_and_bounces" } },
  { body = { regex = "payment (is )?overdue|betalingsachterstand" } },
]
actions.archive = true

Tidy a folder that is not INBOX

A rule watches INBOX unless it names a folder, and runs for every account unless it names one. This one archives list mail you have read, two weeks on, for your personal account only, and leaves flagged threads alone.

rules.toml
[[rules]]
name = "tidy Lists"
account = "personal"
folder = "Lists"
match.read = true
match.flagged = false
match.older_than = "2w"
actions.archive = true

Archive the rest, last

A catch-all for INBOX: archive read, unflagged mail after 90 days. It goes at the bottom of the file. When several rules match a message, the first move or archive in the file wins, so a catch-all near the top would take mail that a more specific rule below it meant to file.

A rule only acts on mail that arrives after you enable it, so on its own this one does nothing for 90 days. To clear the backlog, run it once over older mail, with a dry run first.

rules.toml
[[rules]]
name = "archive the rest"
match.read = true
match.flagged = false
match.older_than = "90d"
actions.archive = true
$ postvak rules apply-existing "archive the rest" --dry-run
$ postvak rules apply-existing "archive the rest"

Try them before they act

A new rule acts only on mail that arrives after you enable it. Before that, check the file and preview each rule on the mail Postvak has cached. --as-of moves the clock, to see what older_than and after will do later, and rules coverage shows mail that several rules compete for. The rules reference has more examples of single rules.

$ postvak rules check
$ postvak rules test "tag security mail"
$ postvak rules test --as-of 2d
$ postvak rules coverage --folder INBOX
